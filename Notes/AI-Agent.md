# AI Agent 笔记

## 一、AI Agent 是怎么让大模型“除了打字还能干活”的？

关键在于**给模型一套工具（Tool），并让它反复调用**。差别不在模型本身，而在流程：

```text
普通对话 AI：你问 → 模型输出文字 → 结束（它看不到你的文件，也不能改任何东西）
AI Agent  ：你给目标 → 模型决定“我要读哪个文件/跑什么命令” → 工具在你电脑上真的执行
                     ↑                                                    ↓
                     └──────── 把工具返回的真实结果喂回模型，继续下一步 ──┘
```

拆开看是四件事：

1. **工具（Tool / Function Calling）**：读文件、写文件、搜索、执行命令、访问网络……
   每个工具都有名字、参数说明和返回格式，模型按这个“说明书”去调用。
2. **执行循环（Agent Loop）**：模型输出一次“调用请求”后，程序**真正执行**它，
   再把结果作为新的上下文交回模型，模型据此决定下一步——直到它认为任务完成。
3. **权限与沙箱**：工具运行在真实机器上，所以必须有权限边界（能读写哪些目录、命令要不要确认）。
4. **规则与记忆**：项目规则文件（`CLAUDE.md` / `AGENTS.md` 等）和跨会话记忆，
   让它在新的会话里也知道“这个项目该怎么干活”。

所以题目里的 Workbuddy、OpenClaw 之所以能写文档、发消息、定闹钟，
本质就是**模型 + 一堆工具 + 一套执行循环**，而不是模型自己变聪明了。

## 二、长期用下来信息太多，“记忆”有限怎么办？

先分清两件事：**模型自身的上下文（Context）是固定的、会被挤掉的**，
所以“记住很多事”不能靠模型，要靠**外部存储 + 按需取回**。常见做法：

| 做法 | 存什么 | 特点 |
| --- | --- | --- |
| **结构化数据库（MySQL）** | 会话记录、任务、用户偏好等需要精确查询的内容 | 可检索、可统计、可审计 |
| **键值存储（Redis）** | 最近几轮对话、临时状态、会话缓存 | 快、适合“短期记忆”，通常带过期时间 |
| **向量数据库 / RAG** | 把历史对话、文档切片后存向量，按语义相似度检索 | 解决“用什么标准找回来”的问题，是长期记忆的主流做法 |
| **文件 / 笔记（Markdown、日志）** | 结论、经验、规则 | 人能直接看懂、能进 Git 版本管理 |
| **摘要压缩** | 把长对话滚成摘要，再参与上下文 | 直接对抗“上下文不够用” |
| **规则文件 / 技能包（Skill）** | 可复用的流程（怎么做某类任务） | 不占对话上下文，需要时才加载 |

实践上一般是**组合**：

- 短期：当前会话上下文（+ 摘要压缩）；
- 中期：Redis 存会话状态、最近消息；
- 长期：MySQL 存事实（我是谁、项目是什么）、向量库存可检索的记忆；
- 流程：写成 Skill/规则文件，避免每次重复解释。

一个很好用的判断标准：**“下次还需要知道吗？”** 需要 → 落盘（数据库/文件/向量库）；
只是一次性的 → 让它待在上下文里，随会话结束消失。

> 这也是我在做题时真实用到的思路：项目规则写进仓库里的 `AGENTS.md`（不占对话上下文、
> 可版本管理、随时可重新读取），长期事实交给 Agent 的记忆功能，具体流程沉淀成 Skill。

## 三、我的理解补充

- Agent 的**能力上限**主要不取决于模型有多聪明，而取决于**接了多少工具、写了多少规则**。
- Agent 越强，越需要人**验证结果**：它说“完成了”不等于真的完成——
  要看 `git diff`、要自己跑一遍、要能解释代码为什么这么写。
- 安全和权限是必须提前想的事：能执行任意命令的 Agent 既能帮你干活，也能误删你的数据。
